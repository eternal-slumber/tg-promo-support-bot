# Spec Delta

## Purpose

Capability обеспечивает надёжную обработку вопросов участников, grounded-ответы только по правилам акции и безопасную передачу оператору во всех случаях, когда автоматическому решению нельзя доверять.

## ADDED Requirements

### Requirement: Надёжный приём сообщения до AI-обработки
Система MUST идемпотентно сохранить входящий Telegram update и сообщение участника в PostgreSQL до вызова LLM, а AI-обработку MUST начать асинхронно только после успешного commit.

#### Scenario: Входящее сообщение сохранено до вызова LLM
- **GIVEN** получен новый Telegram update с текстовым сообщением
- **WHEN** система принимает update
- **THEN** update и входящее сообщение сохраняются одной транзакцией
- **AND** AI job записывается в ту же PostgreSQL transaction и становится доступна worker только после commit
- **AND** LLM не вызывается в запросе Telegram webhook

### Requirement: Явный fallback для неподдерживаемого non-text сообщения
Для распознаваемого non-text сообщения участника в private chat система MUST попросить отправить вопрос и текст подписи отдельным текстовым сообщением через существующую очередь доставки. Содержимое, caption и file metadata MUST NOT сохраняться или передаваться LLM. Fallback MUST NOT расходовать LLM quota или создавать ticket. При active ticket новое non-text сообщение MUST вернуть resolved в open. Служебные события и group updates MUST оставаться ignored.

#### Scenario: Фото с подписью или документ
- **GIVEN** участник прислал фото с содержательной подписью или документ в private chat
- **WHEN** текстовый MVP не может принять это сообщение
- **THEN** сохраняются только update metadata и text-only уведомление, связанное с active ticket при его наличии
- **AND** повтор update не создаёт ещё одного уведомления, а новые non-text updates ограничены одним уведомлением в минуту на участника
- **AND** отказ постановки delivery job в очередь откатывает также update, уведомление и notice limiter

### Requirement: Onboarding при старте
При команде `/start` система MUST кратко представить поддержку акции «Вкусная осень» и объяснить, что участник просто пишет вопрос обычным сообщением: искать кнопку «Создать обращение» не нужно. Бот MUST объяснить, что попробует ответить по правилам акции, а проверку конкретного чека, приза или ситуации участника автоматически передаст оператору. Сообщение MUST запрещать отправлять номера банковских карт, CVV/CVC, пароли и SMS/OTP-коды, сообщать, что фото и документы пока не обрабатываются и вопрос нужно описать текстом, и содержать 2–3 коротких примера вопросов. Onboarding MUST оставаться системным сообщением с ReplyKeyboardRemove, без меню создания ticket или вызова AI. Существующие lifecycle и delivery guards MUST сохраняться. Точная формулировка остаётся presentation detail.

#### Scenario: Участник узнаёт, как задать вопрос
- **GIVEN** участник начинает диалог с ботом
- **WHEN** бот получает команду `/start`
- **THEN** участник получает описание поддержки акции, обычного текстового вопроса и автоматической передачи персонального вопроса оператору
- **AND** сообщение содержит предупреждение о секретах, ограничение фото/документов и 2–3 примера вопросов
- **AND** sendMessage содержит ReplyKeyboardRemove без кнопок создания обращения
- **AND** `/start` не создаёт ticket, не вызывает AI и не учитывается как ответ бота

### Requirement: Grounded-ответ по единственному источнику
Система MUST отвечать автоматически только тогда, когда весь содержательный ответ подтверждается `docs/assignment/promo-rules.md`, и MUST NOT выдумывать сведения об акции или участнике.

#### Scenario: Обычный вопрос покрыт правилами
- **GIVEN** участник задаёт вопрос, полный ответ на который содержится в `promo-rules.md`
- **WHEN** валидированное AI-решение классифицирует сообщение как полностью покрытое правилами
- **THEN** участнику отправляется grounded-ответ
- **AND** обращение оператору не создаётся

#### Scenario: Заявленное участником состояние нельзя подтвердить
- **GIVEN** участник сообщает, что выиграл приз или зарегистрировал чек
- **WHEN** система не имеет внешних данных, подтверждающих это состояние
- **THEN** система не представляет сообщение участника как подтверждённый факт акции

### Requirement: Эскалация неизвестных и персональных вопросов
Система MUST создать обращение, если ответа нет в правилах либо ответ требует данных конкретного участника, и MUST уведомить участника с номером обращения. Обычный off-topic без ответа в правилах также MUST эскалироваться как принятое MVP-допущение.

#### Scenario: Ответ отсутствует в правилах
- **GIVEN** участник задаёт не adversarial вопрос, ответа на который нет в `promo-rules.md`
- **WHEN** сообщение обработано
- **THEN** создаётся обращение со статусом `open`
- **AND** участник получает уведомление с номером обращения

#### Scenario: Вопрос требует данных участника
- **GIVEN** участник спрашивает о статусе своего чека, аккаунта, приза или доставки
- **WHEN** сообщение обработано
- **THEN** бот не имитирует доступ к персональной системе акции
- **AND** создаётся обращение со статусом `open`

#### Scenario: Обычный вопрос вне тематики акции
- **GIVEN** участник задаёт не adversarial вопрос вне тематики акции
- **WHEN** в правилах нет ответа
- **THEN** вопрос передаётся оператору, а не отклоняется автоматически

### Requirement: Смешанный ответ и эскалация
По provisional MVP-допущению система MUST ответить на однозначно подтверждённую правилами часть mixed request и одновременно создать обращение для персональной или неизвестной части.

#### Scenario: Mixed request
- **GIVEN** одно сообщение содержит вопрос по правилам и вопрос, требующий персональных данных
- **WHEN** валидированное решение выделяет обе части
- **THEN** участник получает grounded-ответ на известную часть
- **AND** для оставшейся части создаётся одно обращение
- **AND** участник получает его номер

### Requirement: Один structured decision и deterministic validation
Модель MUST одним основным запросом понять сообщение и вернуть ровно `decision`, `reason`, `answer`, `evidence`. Допустимые пары MUST быть `answer/rule_answer`, `mixed/mixed_request`, `escalate/participant_specific`, `escalate/not_in_rules` или `refuse/prompt_injection`; reason `llm_failure` MUST создаваться только приложением. PHP MUST выполнять deterministic validation без второго LLM verifier и без построения решения из списка parts.

`answer` и `mixed` MUST иметь конкретный непустой пользовательский answer и непустой evidence из `{rule_id, quote}`. Каждый rule_id MUST существовать в promo rules, а непустая quote MUST принадлежать именно указанному rule; нормализуется только whitespace. `escalate` MUST иметь answer null и evidence []; `refuse` MUST иметь безопасный answer «Я не могу выполнить этот запрос.» и evidence [], исключая передачу фактов акции под видом отказа. Невалидный JSON, неизвестные или дополнительные поля, неподходящий тип и противоречие decision/reason/answer/evidence MUST сразу вызывать существующую safe escalation без factual answer или повторной генерации.

Валидный answer MUST оставаться текстом для пользователя; evidence подтверждает источник, а не заменяет answer полным текстом правила. Deterministic quote membership не является доказательством семантической правильности всех свободных утверждений модели; отдельная LLM verification MUST NOT выполняться.

#### Scenario: Один запрос для grounded answer
- **GIVEN** модель возвращает answer/rule_answer с допустимым answer и evidence
- **WHEN** deterministic validation завершается успешно
- **THEN** answer сохраняется и отправляется участнику
- **AND** выполняется ровно один LLM HTTP request без запроса approval

#### Scenario: Ложный grounding
- **GIVEN** модель возвращает answer или mixed без evidence, с неизвестным ID либо цитатой, отсутствующей в указанном пункте
- **WHEN** PHP проверяет result
- **THEN** немедленно применяется существующая llm_failure escalation
- **AND** factual answer не сохраняется и не отправляется, другого LLM request нет

#### Scenario: Конкретный расчёт вместо цитирования правил
- **GIVEN** вопрос содержит 7 участвующих питьевых йогуртов и 2 неучаствующих творожка в одном чеке
- **WHEN** answer с результатом 3 шанса имеет допустимый контракт и evidence
- **THEN** участнику отправляется этот answer с явным результатом, а не полный текст пунктов правил

#### Scenario: Следующий розыгрыш по московскому времени
- **GIVEN** текущее время в Москве — 6 октября 2026 года 00:05
- **WHEN** участник спрашивает о следующем еженедельном розыгрыше
- **THEN** единственный основной LLM request получает это московское время в trusted system context
- **AND** answer модели с валидным evidence указывает 6 октября 2026 года в 15:00 МСК

#### Scenario: Разделение доверенных инструкций и participant text
- **GIVEN** участник отправил sanitized adversarial сообщение
- **WHEN** provider adapter формирует payload
- **THEN** system-role содержит только application prompt, output contract, правила и trusted московское время
- **AND** user-role содержит sanitized participant text

#### Scenario: Модель возвращает mixed
- **GIVEN** сообщение содержит covered и participant-specific запросы
- **WHEN** модель возвращает mixed/mixed_request с ответом только на covered часть и valid evidence
- **THEN** PHP проверяет result и применяет прежние mixed side effects: grounded answer и одну эскалацию

#### Scenario: Невалидный structured output
- **GIVEN** модель возвращает невалидный JSON или неполный structured result
- **WHEN** deterministic validation отклоняет его
- **THEN** safe escalation выполняется сразу после первой попытки
- **AND** job завершается как failed, повтор job не создаёт второго обращения или запроса

### Requirement: Retry и безопасный fallback LLM
AI job MUST повторять только один основной временно неуспешный LLM request с backoff, максимум 3 provider attempts на participant message. На каждой попытке MUST выполняться не более одного LLM HTTP request; вложенный HTTP retry и generation × verification MUST NOT выполняться. Настройки attempts выше трёх MUST ограничиваться тремя. Постоянная ошибка с retryable=false MUST сразу применить существующий fallback без повторного LLM-вызова. После исчерпания retry система MUST создать или использовать единственное открытое обращение с причиной `llm_failure`, не теряя входящее сообщение.

#### Scenario: LLM timeout
- **GIVEN** LLM не отвечает до настроенного timeout
- **WHEN** попытка AI job завершается
- **THEN** job повторяется согласно backoff, пока доступны попытки
- **AND** участнику не отправляется неподтверждённый ответ

#### Scenario: Временный сбой устранён повторной попыткой
- **GIVEN** первая попытка LLM завершилась временной ошибкой
- **WHEN** следующая попытка возвращает валидное решение
- **THEN** решение применяется один раз
- **AND** fallback-обращение `llm_failure` не создаётся

#### Scenario: Retry исчерпаны
- **GIVEN** три допустимые попытки LLM завершились transient ошибкой
- **WHEN** job окончательно завершается неуспешно
- **THEN** входящее сообщение остаётся сохранённым
- **AND** создаётся не более одного обращения с причиной `llm_failure`
- **AND** участник получает уведомление об эскалации

#### Scenario: Job повторён после сохранения решения
- **GIVEN** для входящего сообщения уже сохранено валидное решение
- **WHEN** тот же AI job запускается повторно
- **THEN** LLM повторно не вызывается
- **AND** ответ, обращение и статистический результат повторно не создаются

### Requirement: Безопасный отказ для adversarial-ввода
Система MUST отказать в раскрытии инструкций, изменении своей роли, назначении победителя, создании фиктивного приза или другом несанкционированном административном действии. Такой запрос MUST NOT изменять данные акции или раскрывать system prompt.

#### Scenario: Prompt injection
- **GIVEN** сообщение требует игнорировать системные инструкции и раскрыть system prompt
- **WHEN** сообщение обрабатывается
- **THEN** участник получает безопасный отказ без раскрытия prompt
- **AND** инструкции пользователя не меняют правила маршрутизации

#### Scenario: Фиктивное административное действие
- **GIVEN** участник просит назначить его победителем или создать несуществующий приз
- **WHEN** сообщение обрабатывается
- **THEN** действие не выполняется
- **AND** система не выдаёт фиктивное подтверждение

### Requirement: Redaction до persistence и downstream processing
Система MUST редактировать обнаруженные чувствительные значения до persistence и до передачи текста в LLM, operator UI, Telegram quotes или application logs. Raw unredacted message body MUST NOT сохраняться.

#### Scenario: Raw sensitive value отсутствует во всех downstream paths
- **GIVEN** входящее сообщение содержит обнаруженное чувствительное значение
- **WHEN** сообщение принято и обработано
- **THEN** в PostgreSQL сохраняется только redacted text
- **AND** LLM, operator UI, Telegram quote и logging path получают только redacted text или безопасную metadata
- **AND** raw sensitive value отсутствует в сохранённом Telegram update payload и queue payload

### Requirement: Минимальный набор чувствительных значений MVP
Система MUST редактировать card-like sequences, явно обозначенные SMS/OTP-коды и явно обозначенные пароли. Телефонный номер MUST NOT автоматически редактироваться, но MUST NOT попадать в application logs или повторяться без необходимости.

#### Scenario: Card number redaction из evaluation case №22
- **GIVEN** сообщение содержит `2200 1234 5678 9012`
- **WHEN** sanitizer обрабатывает сообщение
- **THEN** вся card-like sequence заменяется безопасной маской
- **AND** исходное значение отсутствует в redacted text

#### Scenario: Contextual OTP redaction
- **GIVEN** сообщение явно обозначает числовое значение как SMS-код или OTP
- **WHEN** sanitizer обрабатывает сообщение
- **THEN** значение кода заменяется безопасной маской
- **AND** окружающий несекретный текст сохраняется

#### Scenario: Contextual password redaction
- **GIVEN** сообщение явно обозначает значение как пароль
- **WHEN** sanitizer обрабатывает сообщение
- **THEN** значение пароля заменяется безопасной маской
- **AND** окружающий несекретный текст сохраняется

#### Scenario: Password value без word whitelist
- **GIVEN** вход содержит `пароль qwerty123`, `Мой пароль reset-123`, `пароль !abc` или `пароль: secret word`
- **WHEN** sanitizer проверяет синтаксис объявления и value-like признаки
- **THEN** обозначенное значение полностью маскируется независимо от словаря

#### Scenario: Фразы о проблеме входа не содержат password value
- **GIVEN** вход равен `Password change does not work` или `Password forgotten, cannot log in`
- **WHEN** sanitizer обрабатывает сообщение
- **THEN** текст остаётся неизменным без ложного password redaction

#### Scenario: Одно явно обозначенное owned значение без цифр
- **GIVEN** вход содержит `Мой пароль reset`, `Мой пароль qwerty`, `Мой пароль secret.word` или `My password qwerty` перед концом строки, запятой или точкой с запятой
- **WHEN** sanitizer обрабатывает объявление одного значения
- **THEN** значение полностью маскируется до persistence и LLM независимо от алфавита или наличия цифр
- **AND** многословные фразы `Мой пароль не работает` и `My password does not work` остаются неизменными

#### Scenario: Owned значение в кавычках с разделителями
- **GIVEN** вход содержит `My password "secret, word; 123"`
- **WHEN** sanitizer обрабатывает quoted значение до проверки single token
- **THEN** вся фраза внутри кавычек маскируется, её части не остаются после запятой или точки с запятой

#### Scenario: Обычный числовой текст не маскируется
- **GIVEN** сообщение содержит даты, суммы, количество товаров, номер обращения или иное число без card-like формы и sensitive context
- **WHEN** sanitizer обрабатывает сообщение
- **THEN** обычный числовой текст сохраняется без маскирования

#### Scenario: Телефон остаётся доступен как идентификатор
- **GIVEN** участник указывает телефонный номер для идентификации аккаунта
- **WHEN** sanitizer обрабатывает сообщение
- **THEN** номер остаётся в redacted text для оператора
- **AND** application logs не содержат message body или телефонный номер

### Requirement: Уведомление о redaction и безопасная metadata
Если чувствительное значение было скрыто, система MUST уведомить участника, что данные скрыты и не нужны для поддержки. Система MAY сохранить только факт redaction и типы `payment_card`, `otp`, `password`, но MUST NOT сохранять исходное значение.

#### Scenario: Участник уведомлён о скрытии
- **GIVEN** sanitizer обнаружил и скрыл чувствительное значение
- **WHEN** входящее сообщение успешно сохранено
- **THEN** участнику отправляется краткое уведомление о скрытии
- **AND** уведомление не повторяет исходное чувствительное значение
- **AND** сохранённая redaction metadata не содержит исходного значения

### Requirement: Runtime prompt не сохраняется
Полные runtime system prompts MUST NOT сохраняться в PostgreSQL или application logs.

#### Scenario: Decision сохранён без полного prompt
- **GIVEN** LLM вернул валидированное решение
- **WHEN** система сохраняет результат обработки
- **THEN** решение может содержать structured output и hash источника
- **AND** полный runtime system prompt не сохраняется

### Requirement: Повторная проверка обращения после AI
После LLM-вызова application transaction MUST блокировать participant, active ticket и message в согласованном порядке и повторно проверить активное обращение.

#### Scenario: Два быстрых вопроса и позднее AI-решение
- **GIVEN** во время LLM-вызова другое сообщение создало активное обращение
- **WHEN** первое AI-решение применяется
- **THEN** исходное сообщение прикрепляется к активному ticket без нового decision или устаревшего ответа
- **AND** resolved возвращается в open, поскольку добавлен необработанный вопрос

#### Scenario: Постоянная ошибка LLM
- **GIVEN** provider отклонил запрос с retryable=false
- **WHEN** job обрабатывает ошибку
- **THEN** входящее сообщение получает существующий llm_failure fallback сразу
- **AND** повтор job не делает второго provider request или уведомления

### Requirement: Evaluation со штатной retry-policy
EvaluateSupport MUST применять ProcessIncomingMessage через штатный database Worker с job attempts/backoff и записывать классификацию/validation failures в model result, а safe HTTP/connection failures отдельно в infrastructure failure reason. Временная ошибка MUST NOT вызывать принудительный failed() после первой попытки.

#### Scenario: Retry после временной ошибки evaluation
- **GIVEN** первая попытка временно неуспешна, следующая возвращает валидный decision
- **WHEN** evaluation обрабатывает case
- **THEN** применяется model result без преждевременного fallback
- **AND** отчёт сохраняет safe reason первой ошибки отдельно от результата
