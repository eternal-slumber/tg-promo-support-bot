# Spec Delta

## Purpose

Capability определяет проверяемую семантику обязательных метрик поддержки и обеспечивает их детерминированный расчёт по сохранённому состоянию без повторного обращения к LLM.

## ADDED Requirements

### Requirement: Provisional метрика bot resolved
Единицей `bot resolved` MUST считаться реально доставленный самостоятельный ответ бота по правилам без обращения (`outbound`, `bot`, `ticket_id = null`, `sent`, ненулевой `delivered_at`). Метрика подтверждает Telegram delivery, а не решение проблемы участником. Безопасный `refuse` с фиксированным текстом отказа, mixed request, уведомления об эскалации и системные предупреждения MUST NOT учитываться как `bot resolved`. Счётчики подготовленных ответов и delivery states MUST также исключать refuse.

#### Scenario: Полностью автоматический ответ учтён
- **GIVEN** для входящего сообщения сохранён grounded-ответ
- **AND** обращение для сообщения не создано
- **AND** Telegram delivery зафиксирована как `sent` с ненулевым `delivered_at`
- **WHEN** рассчитывается статистика
- **THEN** счётчик `bot resolved` увеличивается на одну единицу

#### Scenario: Mixed request не учтён как bot resolved
- **GIVEN** бот ответил на известную часть сообщения и создал обращение для оставшейся части
- **WHEN** рассчитывается статистика
- **THEN** сообщение не включается в `bot resolved`

#### Scenario: Отказ не считается ответом по правилам
- **GIVEN** безопасный refuse отправлен участнику без ticket
- **WHEN** рассчитывается статистика
- **THEN** он не включается в `bot resolved` или счётчики подготовленных ответов и delivery states

#### Scenario: Sent без подтверждённого времени доставки
- **GIVEN** bot answer имеет статус `sent`, но `delivered_at` отсутствует
- **WHEN** рассчитывается статистика
- **THEN** он не включается в `bot resolved`

#### Scenario: Неотправленный ответ не улучшает показатель
- **GIVEN** самостоятельный ответ бота сохранён в состоянии `pending`, `failed` или `cancelled`
- **WHEN** рассчитывается статистика
- **THEN** он не входит в `bot resolved`
- **AND** UI учитывает его среди подготовленных ответов и отдельно в соответствующем delivery state

### Requirement: Provisional метрика escalated
До уточнения менеджером единицей `escalated` MUST считаться созданное обращение, независимо от числа сообщений в его истории. Повторная обработка update или job MUST NOT увеличивать метрику.

#### Scenario: Созданное обращение учтено один раз
- **GIVEN** для участника создано обращение
- **WHEN** рассчитывается статистика
- **THEN** `escalated` увеличивается на одну единицу
- **AND** дополнительные сообщения в этом обращении не увеличивают показатель

### Requirement: Provisional среднее время ответа оператора
Response time MUST рассчитываться от времени создания ticket до `delivered_at` первого успешно отправленного ответа оператора. `first_operator_replied_at` MUST фиксироваться в одной transaction с успешной доставкой и MUST NOT устанавливаться при подготовке, ошибке или отмене ответа. Обращения без отправленного ответа оператора MUST NOT входить в среднее. Отменённые operator replies MUST учитываться отдельным счётчиком.

#### Scenario: Ticket с первым ответом включён в average
- **GIVEN** обращение создано в известный момент
- **AND** первый ответ оператора успешно отправлен позднее
- **WHEN** рассчитывается среднее время ответа
- **THEN** для обращения используется разница между этими двумя моментами

#### Scenario: Ticket без ответа исключён из average
- **GIVEN** у обращения нет успешно отправленного ответа оператора
- **WHEN** рассчитывается среднее время ответа
- **THEN** обращение не влияет на числитель и знаменатель среднего

#### Scenario: Доставка после отменённого ответа
- **GIVEN** сохранённый ответ оператора не доставлен и отменён
- **WHEN** оператор сохраняет новый ответ и Telegram принимает его позднее
- **THEN** время первого ответа определяется успешной отправкой нового сообщения, включая задержку доставки
- **AND** повторные jobs и последующие ответы не меняют первый timestamp

#### Scenario: Исправление исторических данных
- **GIVEN** timestamp первого ответа был записан при подготовке сообщения
- **WHEN** применяется forward migration
- **THEN** timestamp пересчитывается по минимальному `delivered_at` отправленных operator replies
- **AND** tickets без таких ответов получают `null`

### Requirement: Детерминированный расчёт
Все обязательные метрики MUST вычисляться только из сохранённых сообщений, решений и обращений. Просмотр статистики MUST NOT вызывать LLM или изменять учитываемое состояние.

#### Scenario: Statistics from persisted state
- **GIVEN** в PostgreSQL сохранён набор bot-resolved сообщений, обращений и ответов оператора
- **WHEN** оператор открывает статистику повторно без изменения данных
- **THEN** система показывает те же значения всех трёх метрик
- **AND** внешние AI и Telegram API не вызываются
